\begin{abstract}
    Pattern matching appeals to functional programmers for its expressiveness
    and good cost model, but it fails to express certain computations without
    verbosity. %
Verbosity can be reduced by using extended forms of pattern
    matching, but extensions are not standardized, and making certain extensions
    like or-patterns and pattern guards cooperate in a large-scale programming
    language is a significant implementation challenge that has not seen success
    until recent years. %

    
    Alternatively to pattern matching, computations can be expressed succinctly
    by using equations, as has been demonstrated by the Verse programming
    language. %
But such computations may have time and space costs that can
    be hard to predict. %
As a compromise, we ~propose a new
    calculus,~\ensuremath{V^{-}}, which~uses equations in a limited way that
    makes time and space costs easy to predict. %
In comparative examples,
    \ensuremath{V^{-}}~ expresses computations as succinctly as pattern matching
    with popular extensions- namely, side conditions, or-patterns, and pattern
    guards- and just like pattern matching, it can be compiled to a decision
    tree. %

    To show that \VMinus has the same cost model as pattern matching, we present
    formal rules and a Standard ML implementation for the \ensuremath{V^{-}}
    match compiler, and we evaluate our implementation with micro-benchmarks and
    a proof that our compilation algorithm preserves the desirable decision tree
    height invariants. %


\end{abstract}

But no popular programming language lets you write all three of the
examples shown:
% programs, because none has all three of these extensions: 
Haskell lacks
(binding) or-patterns\footnote{Non-binding or-patterns have existed in GHC only
as of 2023.}, OCaml lacks guards, other languages lack side conditions, and so
on. %
And we~find the extension story somewhat unsatisfying: Even if one language had
all three of the extensions used in
\crefrange{fig:pmsideconditions}{fig:pmorpats}, there are the other extensions,
like nonlinear patterns and bidirectional matching,  that appear in neither
Haskell nor OCaml. %
As~an alternative, we~show that the expressive power of 
pattern matching, including all these extensions,
can be provided by a design that uses \emph{equations}. %

Our work is inspired by the effective use of equations in
the functional logic programming language Verse,
or rather, the Verse Calculus,~\VC~\cite{verse}. %
Each of the examples in \crefrange{fig:pmsideconditions}{fig:pmorpats} is easily
and concisely written using equations (Figure~\ref{fig:verseextfuncs}).

In~\VC, names can be introduced with the existential {$\exists$} before they are
given a binding. %
Bindings are given by equations of the form $x = e$, which unify their left- and
right-hand sides at runtime. %
Unification (and indeed any \VC expression) can \textit{succeed} or
\textit{fail}, letting programmers ``guard'' an expression with equations and other
expressions.

And~\VC~can do even more: the calculus easily encodes nonlinear patterns (and
even more expressive constructs): see Section~\ref{freeextensions}. %

But the cost model of functional logic languages like~\VC~can be challenging:
because unification under equations can backtrack at runtime, code with
equations can run in exponential
time~\cite{hanus2013functional,wadler1985replace,clark1982introduction}. %
And code that returns multiple values by nesting Verse's \textbf{choice}
operator can quickly become exonential in space usage, too~\cite{verse}.

Pattern matching, by contrast, can be compiled to a~\it{decision tree}, a data
structure that enforces linear runtime performance by guaranteeing no part of
the matched expression will be examined more than once~\cite{maranget}. %
A decision tree does not backtrack: once a program makes a decision based on the
form of a value, it does not re-test it later with new information. %
Furthermore, a decision tree can be space-optimized so that all leaves are
unique by reducing to a DAG via a shared continuation.

Pattern matching tempts us with its desirable cost model, but challenging
questions remain for the modern implementor of both a new and an existing
programming language. %
How much work would it be to add binding or-patterns to GHC? %
How about nonlinear patterns? %
How much work would it be to add guards to OCaml? %
And finally: in a complex codebase like GHC's, is it reasonable to assume that
adding a new extension to pattern matching will not introduce a corner case that
makes pattern matching unsound? %

These questions motivate a somewhat hopeful one: what if we instead start with a
new language and use equations from the start, and engineer the equations to be
performant like pattern matching? 

Our answer to this question, and primary contribution, is a new core calculus
and implementation of expressive equations and an accompanying compiler which
produces a decision tree. % 

Being inspired by~\VC~but reduced to the absolute essence of only
decision-making, it is called~\VMinus (``V-minus''). %



\section{Syntax and Formal Semantics of~\VMinus}
\label{vminus}
\VMinus has equations and choice, like~\VC, but it does not have multiple
results or backtracking. %
To eliminate multiple results, expressions in~\VMinus evaluate to at most one
result, and the logical ``choice'' operator only~\it{guards} computation; it~is
not a valid form of expression like in \VC. %
To~eliminate backtracking, the compiler rejects a~\VMinus program
that would need to backtrack at runtime. %
To provide an efficient and
backtracking-free cost model to which~\VMinus can be compiled, we~introduce
a core language of decision trees,~\D, in Section~\ref{d}. %

\VMinus, like \VC, easily expresses all of the previous examples
(Figure~\ref{fig:vminusfuncs}). %
Furthermore, \VMinus also allows for some constructs that aren't expressible
with these extensions at all (Section~\ref{freeextensions}).

Because we are comparing $V^-$ with pattern matching, we strove in our
    design to model around a ``decision wrapping construct'' analogous to
    \textit{case} or \textit{match} rather than to have equations in any
    syntactic position. % 
    Inspired by Dijkstra, we chose the \iffibf construct~\cite{dijkstra}: a
    wrapper for a list of ``guarded expressions.'' %
    In our case, equations and conditional expressions make up the guards. %
    
    % Though our guards are quite different from patterns, the \iffibf construct 
    % is similar to \textit{case}/\textit{match}.

        There are two small syntactic details: a guarded expression $G$ in an
        \iffibf is separated from its neighbors by a \dbar, and each guard $g$
        is separated from its neighbors by a semicolon. %
        
        \VMinus enforces the ``no backtracking at runtime'' principle by
        construction: names in \VMinus are expressions, not values, and
        unification is permanent. %
        This means that a variable is unified with a
        value once, either by = or under a lambda, and there is no mechanism 
        for re-binding it under a different execution context like in \VC. %
        Furthermore, because choice only guards computations, the programmer can't write the kinds of nested choice 
        expressions that lead to exponential runtime in \VC. %

        Even without backtracking, \VMinus can still express computations that 
        are seemingly ``out of order.'' The following is valid in \VMinus:

        \begin{example}[Out-of-order solving] 
          $\exists\; x~y~z.~z = y;~y = x;~x = \mathit{3}$ 
        \end{example}

        The key insight of how \VMinus remains expressive in the absence of
        backtracking is \textit{compile-time dependency analysis}. %
        Before running the code, the compiler can determine if there exists a
        valid sequence of equations such that executing the sequence in order
        will never reference an unbound name. %
        If such a sequence exists, the compiler transforms the program to follow that sequence. %
        If it cannot find one, the compiler rejects the program. %
        Under the hood, the compiler does this by building a dependency graph
        between variable binding sites and traversing it from the root. %

    \subsubsection{Expressions}
    
    \newcommand\GNoTree{\vmrung~\rightsquigarrow~\uppsidown} 
    
    In~\VMinus, an expression never returns multiple values, though it
    can~\textit{fail}. % 
    Specifically, a~\VMinus~expression evaluates to produce a
    single~\it{result}, which is either a single value $\v$ or~\fail. %
    \begin{center}
      \(\result\;~\rm{::=}\;~\v\;~\vert~\;~\fail~\)
      \qquad     
      \(\showvjudgement{Eval}{\vmeval}\)
    \end{center}

    For example, the~\VMinus expression {\tt{((}\ttbackslash\tt{x. x) K)}}
    succeeds and returns the value~\tt{K}. %
    The~\VMinus expression~\tt{if~~fi}, the empty~\tt{if-fi}, always {\fail}s. %


    \subsubsection{Names and refinement of environments}

    In~\VMinus, like in~\VC, names can be introduced with the existential
    {$\exists$} before they are given a binding. %
    Bindings are given by equations in guards~(\ref{guards}). %
    When a name is introduced with {$\exists$}, it is bound in the
    environment~\Rho\ to $\bot$ (bottom). %
    Success of a guard only~\it{refines} the environment; that~is, when
    $\grefine[solution=\Rhoprime]$, we~expect $\rho~\preceq~\Rhoprime$. The
    definition of $\preceq$ on environments is given below. %
    
    \smallskip 
    
    \textbf{Refinement ($\preceq$) of environments and variables}

{\scriptsize
    \begin{align*}
    \rho~\preceq~\Rhoprime~&\text{ when }\dom\rho~\subseteq~\dom~\Rhoprime\\
    &\text{ and }\forall x~\in~\dom~\rho:~\rho(x)~\leq~\Rhoprime(x) \\
    &\forall~v.~\bot~\leq~v~\land~v~\leq~v
    \end{align*}
}

    Refinement on bound instances in environments is trivial: 
    $\bot$ can refine to a value, and once a value is bound, 
    it is never rebound. %

    The only place $\bot$ can appear is on the right-hand side of a variable in
    an environment. This means ``partially refined'' constructor application is
    disallowed: a constructor $K$ can never be applied to $\bot$. %
    
    \subsubsection{Guards}
    \label{guards}
    

    Like~\VC,~\VMinus has a semantics built around the philosophy of "pick an
    equation and solve it" (now thinking with guards rather than equations). %
    Picking and solving a guard in~\VMinus is similar to picking and solving an
    equations \VC: the program picks one out of a context (\context), attempts
    to solve it, and moves on. %

    \(\showvjudgement{Solve-Guards}{\vmgs}\)

Given any such $\rho$, a guard~\g\ either refine $\rho$
($\Rhoprime$) or is~\bf{rejected}. %
We use the symbol $\dagger$ to
represent rejection, and if any guard in a list is rejected, the entire list of
guards is rejected. %

\(\showvjudgement{Refine}{\grefine[solution=\rho']}\)
\hspace{2in}
\(\showvjudgement{reject}\gfail\)

  For example, in the~\VMinus expression~\tt{if E x. x = K; x = K2 -> x fi}, the
  existential (in concrete syntax,~\tt{E}) introduces~\tt{x} to~\Rho\ bound to
  $\bot$, producing the environment $\bracketed{x~\mapsto~\bot}$. %
The guard
  \tt{x = K} successfully unifies~\tt{x} with~\tt{K}, producing the environment
  $\bracketed{x~\mapsto~\tt{K}}$. %
The guard~\tt{x = K2} attempts to unify~\tt{K}
  with~\tt{K2} and is rejected with $\dagger$. %


The semantics processes a~\it{list} of guards~\gs in a guarded
expression \G: the program picks a guard from~\G, attempts to solve it to refine
the environment or fail, and repeats.~\VMinus can only pick a guard out of \G\
that it \it{knows} it can solve. %
\it{Knowing} a guard can be solved can be determined in~\VMinus before code is
executed by building a dependency graph between variable binding sites and
traversing it from the root. %
If~\VMinus can't pick a guard and there are
guards left over, the semantics gets stuck before code is executed. %

Below are several examples of how \VMinus is interpreted, using abstract syntax. 

\begin{example}
  $\exists\; x\;y.\; K~x~1 = K~2~z~~~\rightarrowtail~~~\{x \mapsto 2,~y\mapsto1\}$  
\end{example}


The bidirectional constraint $K~x~1 = K~2~z$ is solved by breaking the term into
sub-equations $x = 2;~1=z$, and the derivation succeeds with an extended
environment. 

\begin{example}
  $\exists\; x\;y.\; x=K~y;~y = K~0~~~\rightarrowtail~~~\{x \mapsto K (K~0),~y\mapsto~K~0\}$  
\end{example}

The semantics first ``picks'' the guard $y = K~0$ since it is immediately
solvable. %
Once $y$ is bound to $K~0$ in the environment, $x=K~y$ becomes solvable, and
the derivation succeeds with an extended environment. 

\begin{example}
    $\exists\; x\;y.\; x=K~y;~y = K~x~~~\rightarrowtail~~~\dagger$ 
\end{example}

Here $x$ and $y$ are circularly dependent, so the program cannot make progress,
and the derivation fails with $\dagger$. 

\begin{example}
    $\exists\; x.\;x=3=x=4~~~\rightarrowtail~~~\dagger$ 
\end{example}

Here $3$ cannot be unified with $4$ no matter the order in which 
the semantics picks the guards, so the derivation fails with $\dagger$.

\subsection{Extensions for free}
\label{freeextensions}

In addition to subsuming the three extensions we mentioned, \VMinus also allows
for some constructs that aren't expressible with these extensions at all: 

\scriptsize{
\begin{verbatim}
  val nonlinear_binding = \xs. 
    if E y ys. xs = cons y (cons y) ys -> ys fi 

    val bidirectional_binding = 
      if E y ys. cons A ys = cons x AS -> y fi 

    val lenient_binding = \xs.
      if E x y z. x = y; z = cons y ys -> x fi 
\end{verbatim}}

\normalsize
    
Nonlinear patterns (patterns that use a name more than once) appear in some
programming languages like Erlang, but like our prior examples, they are also
not standardized. %
\textit{Bidirectional binding} (patterns and values on both sides of an
equation) and \textit{leniency} (bindings in non-left-to-right order) do not
appear in any popular functional programming language at all. % 

Where pattern-matching needs to be extended to encapsulate such features,
\VMinus (and \VC, which can also express these examples) gets them for free. %
But what about cost? %
In the following section, we demonstrate that \VMinus, with its additional
expressiveness, has the same cost model as pattern matching. %

\section{\VMinus~compiles to a decision tree}
\label{d}

Like pattern matching, \VMinus~compiles to a decision tree whose height is 
linear with respect to code size. % 
Also like pattern matching, \VMinus is amenable to \textit{heuristic
compilation}\cite{macqueen1985tree}, by which the shape of the decision tree can be
optimized in individual cases by a heuristic. % 

To formalize decision trees, we use a new language, \D, which generalizes the
trees found in~Maranget's formalization~\cite{maranget}. %

    \subsection{The~\DTran\ compiler:~\VMinus $\rightarrow$~\D}


    When presented with an~\iffibf,~\DTran~invokes~\Compile with context~\ctx. %
    \Compile~first desugars the~\iffibf by expanding choice to multiple~\iffibf
    branches with a desugaring function~\ITran: 
    
    % todo put this on one line
    {\scriptsize \[
      \itran{if\dots \dbar~gs_{1};~\choiceg{gs_{2}}{gs_{3}};~gs_{4}~\rightarrow e~\dbar~\dots~fi}
      ==
      {\bf{if}~\dots~\dbar~gs_{1};~gs_{2}~\rightarrow e~\dbar~gs_{3};~gs_{4}~\rightarrow e~\dbar~\dots~\bf{fi}}
    \]}

    The duplicated instances of $e$ in the image can be optimized away with the
    classic decision tree DAG optimization. 

    With the desugared~\iffibf,~\Compile\ then repeatedly chooses a guarded
    expression $G$ and applies one of the compilation rules below. %

    The key insight of the compiler is that it chooses a guarded expression
    based on its ability to compile a guard $g$, and that this decision happens
    the exact same way as in the \VMinus interpreter. %
    In formal terms: when \VMinus chooses a guard $g$ and \DTran chooses a guard
    $g'$ from the same guarded expression $G$, $g = g'$. %
    Like \VMinus, the compiler can only choose a guard in which each expression
    contains names that are bound upstream (in this case, we say the expression
    and its names are \textit{known}). The only difference with \VMinus is that
    instead of an environment \Rho, the compiler uses a context~$\ctx$~in which
    each name maps to $known$ if the name has a prior binding site or $unknown$
    otherwise. 
    
    $\ctx(x) = \mathit{known~|~unknown}$
    
    \knownj~when all names in $e$ have been bound. 
  
    The rules are applied in order according to a \textit{heuristic}
    (Section~\ref{reductionstrats})--- a common strategy in match compilation. 

    \Compile terminates when it inserts a final~\it{match} node (with rule
    \textsc{Match}). %
    A~\it{match} node is inserted for a right-hand side expression~\expr when the
    list of guards preceding~\expr is empty or a list of assignments from names
    to unbound names. %
    Termination of~\DTran\~is guaranteed because each recursive call passes a
    list of guarded expressions in which the number of guards is strictly
    smaller, so eventually the algorithm reaches a state in which the first
    unmatched branch is all trivially-satisfied guards. %

    If~\Compile\ cannot choose a $g$ of one of the valid forms, it halts with an
    error. %
    This can happen when no $g$ is currently solvable in the context, as
    determined by the same algorithm that~\VMinus uses to pick a guard to solve,
    or when the program would be forced to unify incompatible values, such as
    any value with a closure. %

\section{Evaluation and Analysis}

We evaluate two properties of our code: 

\begin{enumerate}
  \item \textit{Correctness:} Interpreting \VMinus code produces the same result as
  compiling it to a decision tree and interpreting the tree. 
  \item \textit{Performance:} The compiler produces a tree whose height is
  linear in the size of the source code. 
\end{enumerate}


To evaluate correctness and performance, we implemented an interpreter for
\VMinus, its compiler, and an interpreter for the resulting decision trees, and
ran a differential correctness and performance analysis across a suite of 32
microbenchark tests. %
For further reference on our evaluation strategy, Figure~\ref{fig:evaluation} in
the Appendix shows the map of our testing framework. % 

\subsection{Microbenchmark tests}

Each microbenchmark test runs a program $p$ through the \VMinus
interpreter to produce a result $r$ and running it through the \DTran compiler and
\D interpreter to produce a result $r'$. %
For correctness, the test ensures that $r = r'$. % 
In the case that $r$ and $r'$ are failures, the test ensures the failure is of
the same kind. %
For performance, the microbenchmark measures the size of the source \iffibf and
target decision tree and ensures they are equal. % 

We built the set of test programs $p_1, p_2, \dots p_{32}$ by case split on each
expression type and minimal unique example of \iffibf. 

All of our tests produce equivalent results with correct-sized decision trees. 

While any given decision tree is height-bound by the invariant, the exact shape
of the tree depends on heuristics, a fact that is well-examined in the
literature\cite{macqueen1985tree,maranget,scottramsey}. %
 Our decision trees adhere to this principle by the same means of a
\textit{heuristic hole}. % 
When presented with more than one 'chooseable' equation in the context, the
compiler selects one by a heuristic which is easily adjustable within the source
code. %
As with any match compiler with a heuristic, ours can be given an optimal and a
pessimal example. We highlight these in the following section. % 

\subsection{Heuristic Comparison and Reduction Strategies}
\label{reductionstrats}

      In our implementation, I apply the~\textsc{Test} rule before other rules,
      having found in our experiments that this heuristic leads to the smallest trees. %
      A~risk of inserting a \it{test} node before a \it{let-unless} node is that
      if there are many shared names across branches, a \it{test} node will
      introduce those names in \it{let-unless} nodes in each subtree. %
      It is possible to insert \it{let-unless} nodes before \it{test}
      nodes, in which case those names will be bound
      only once. %
      The risk of the \it{let}-first strategy
      is that if there are many names used in only one subtree of a \it{test},
      these names will be introduced to \it{all} branches. %
      The extra bindings may harm performance by bloating an environment in an
      interpreter or thrashing the icache if the tree further is compiled to
      machine code. %

    In the implementation,~\DTran\~first introduces all the names under the
    all existential $\exists$'s to a context which determines if a name is
    \it{known} or~\it{unknown}, applying the~\textsc{Exists} rule is applied
    all at the start. %
    At the start of compilation, each name introduced by $\exists$ is~\it{unknown}
    in a context~\ctx. %
    Since all names in the program are unique at this stage, there are no clashes. %


\subsection{Proof: \Compile~Preserves the Decision Tree Invariant}

      Proof obligation: if a step of compilation adds a node~$n$~to the decision
      tree, $n$ will not be duplicated in its children. %

\begin{proof}

      \textit{By induction on the compilation judgement. }%

      In the cases of \textsc{Exists}, \textsc{Elim-Vcon}, \textsc{Expand-Vcon},
      and \textsc{Fail}, the compiler does not insert a node, so we are
      trivially done. %

      In the case of \textsc{Match}, the inserted~$\mathit{match~e}$ node has no
      children, so we are trivially done. %

      In the case of \textsc{Test}, the compiler inserts a \textit{test} node
      with~$n$~children in~$\overline{\tree}$, and a child at index~$i$~is
      guarded by $x$'s match on a distinct value constructor $K_i$ over fresh
      names $\overline{y}_i$. %
      It also inserts a default branch~$\tree_0$ guarded by a unique value
      constructor $K_0$.% 
      For each child in~$\overline{\tree}$, the compiler ensures that each
      instance of~$x$~is substituted for~$K_i~\overline{y}_i$~(and likewise for
      $K_0$ in~$\tree_0$).%
      This means that $x$~will never appear in any subtree of the inserted node,
      which in turn means there can never be another \textit{test} node
      for~$x$~in any of the inserted node's children. %
       This invariant is the heart of the match compiler: a value is examined
      \textit{at most once} when the compiled tree is traversed. %
      Each subtree follows the height invariant according to the inductive
      hypothesis, and we are done. %

      In the case of \textsc{Let-Unless}, the the expression~$e'$ is being
      substituted out in the subtrees. % 
      This means that~$e$~will run once in the inserted node and never again in
      the subtrees. % 
      The invariant is preserved, and we are done by application of our
      inductive hypothesis to the subtrees. 
      
      The case for \textsc{Let-If} is similar: in each subtree of the inserted
      node, either~$e'$~or the equation~$x = e'$~is substituted for a name or
      \textbf{fail}, meaning~$e'$ will be evaluated no more than once
      and~$x$~will be compared to~$e'$ no more than once.  The invariant is
      preserved, and we are done by application of our inductive hypothesis to
      the subtrees. 
\end{proof}



    \section{Related and Future Work}

    This paper builds on Augustsson et al.'s Verse Calculus~\cite{verse} and
    decision trees~\cite{maranget}. %
    Augustsson et al. give the formal rewrite semantics for the Verse Calculus;
    Maranget gives an elegant formalism of decision trees and a translation
    algorithm from patterns to decision trees. %
    We~attempted to imitate the behavior of the rewrite semantics of~\VC in the
    big-step semantics of~\VMinus by manually rewriting terms in~\VC and
    creating rules that would imitate the ultimate result of term-rewriting. %
    
    We~chose a big-step semantics because the big-step evaluation rules closely
    mirrors the structure of our interpreters and compiler, which helped us
    reason about the code. For our microbenchmark-based approach, this equivalence 
    between code and rules was valuable for reasoning. %

    Maranget's formalism was the foundation off of which we~built~\D. %
    
    Extensions to pattern matching, and how they appeal to language designers,
    find an excellent example in the proposal for pattern guards in
    Haskell~\cite{guardproposal}. %
    The authors describe pattern guards and transformational patterns (another
    extension to pattern matching), both of which allow a Haskell programmer to
    write more concise code using pattern matching. %
    Or-patterns are documented in the OCaml Language Reference
    Manual~\cite{ocaml}. %
    
    \textit{Compiling Pattern Matching}~\cite{augustsson1985compiling}~ gives a
    foundation in compiling pattern matching. %
    Scott and Ramsey's \textit{When Do Match-Compilation Heuristics
    Matter?}~\cite{scottramsey} have a crisp example of a match-compilation
    algorithm (pattern matching to decision trees). %
    Scott and Ramsey's algorithm
    structurally inspired ours, and studying the source code from the paper
    aided our implementation. %

    For future work, our top priority is to prove that \DTran~preserves
    semantics. %
    Secondarily, we~plan to formally prove that \VMinus subsumes pattern
    matching by showing that the translation of pattern-matching code to \VMinus 
    does not increase code complexity. 

    Finally, we~would like to explore exhaustiveness analysis, or coverage
    checking, of~\VMinus. %
    Exhaustiveness analysis can warn programmers of a missing or extraneous
    alternative in a~\it{case} expression. %
    Owing to its significantly more flexible structure,
    however,~\iffibf may prove trickier to analyze. %
    And exhaustiveness in the presence of arbitrary side conditions, both in
    pattern matching and \VMinus, is NP-hard. % 
    But there is hope: proving that the translation from pattern matching to
    \VMinus does does not \textit{weaken} exhaustiveness analysis can give a
    convincing argument that the language does ``as good a job'' at exhaustiveness
    as pattern matching. 

    \section{Conclusion}

    We~have introduced~\VMinus, a~language that makes decisions using
    equations.%
    By~example, we have shown that programs written in~\VMinus can be as
    succinct as equivalent programs written using pattern matching. %
    And~to~show that equations can be compiled to efficient decision trees, we
    have introduced~\D and~\DTran and showed their correctness and efficiency in
    under a suite of microbencharks. In doing so, we~have demonstrated that
    programming with equations is a promising alternative to pattern matching. %
